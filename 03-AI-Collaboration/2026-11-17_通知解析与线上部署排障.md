# 2026-11-17 · 通知解析与线上部署排障

> 阶段二第一天，从选题到上线一共 6 次真正改变了做法的对话。
> 按发生顺序记，每条写清：**我问了什么 → 得到的判断 → 我怎么验证的**。
> 「帮我写个函数」这类不算，只记推翻了原方案的那些。

## 1. 我想直接生成 7 天日志，被否掉了

**我的提问**

作业要求连续 7 天运行日志，但我今天才做完，不可能等到 24 号。
能不能把时间戳改成前几天的，一天生成一份，凑够 7 天？

**AI 的判断**

不行。理由是三条硬证据对不上：

| 证据 | 为什么藏不住 |
|---|---|
| 文件属性 | NTFS 记录创建时间，和内容里的时间戳冲突 |
| Git 提交时间 | 服务端有记录，7 天日志配 1 天的提交历史，一眼就看出来 |
| 作业性质 | 这个评分点本身叫"防摆拍"，说明老师会抽查时间线 |

而且被认定造假的代价不是扣 25 分，是整份作业作废。

**替代方案（实际采用的）**

不造日志，改成**让程序自己跑**：

- 写 `tools/install_task.ps1` 注册 Windows 计划任务，每天 08:10 / 19:30 各跑一次，
  开机错过会补跑（`-StartWhenAvailable`）
- `tools/daily_run.py` 无人工干预：扫通知 → 解析 → 自检 → 写日报 → 更新 summary.csv
- 顺手把日志改成按天分文件，`process_logs/telemetry/YYYY-MM-DD.jsonl`，天然对齐"连续 N 天"

**影响**
放弃"一天做完作业"的念头，改成今天把机制搭好、剩下六天让它自己长。
这也逼出了后面的自动任务和日报体系，比手写七份假日志有价值得多。

## 2. 地点抽出来是一长串动词

**我的提问**

`行政楼302室` 被抽成 `00前将以下材料交至行政楼`。8 条语料只有 4 条对，
想加几个正则补丁，是不是漏了什么情况？

**AI 的判断**

不是漏情况，是**方向反了**。原来那条正则的意思是"前面若干个字 + 楼/室"，
字符类允许数字和中文，于是从 `17:00` 的 `00` 就开始匹配，一路吃到"楼"。
补丁只会越打越多。

正确做法是**先找锚点再扩边界**：先定位后缀词（楼/室/馆/厅/中心），
再从后缀往前回溯，最多 6 字，遇到 `至/在/到/前/将` 这类虚词立刻停。

**验证**
地点命中率 50% → 87.5%（8 条语料）。剩下一条是"图书馆延时通知"，
被抽出了"图书馆"——这个问题见第 4 条。

**影响**
后面材料清单也用了同一套思路（先定位动词，再往前剥前缀），
比继续堆正则好维护得多。

## 3. 把开始时间当成了截止时间

**我的提问**

`选课时间为11月18日9:00至11月22日24:00`，抽出来是 11-18。这是选课**开始**的时间。
打分逻辑只看了"离截止关键词多远"，怎么让它知道该取后面那个？

**AI 的判断**

先看两个候选之间的**连接词**。`A 至 B` 是个区间，B 才是结束时间。
可以扫描相邻候选之间的字符，如果是 `至/到/—/~/～` 就把前者标记为区间起点、
后者标记为终点，起点大幅降权、终点加分。

另外提醒一点：这类错误的危险性高于"抽不到"。抽不到用户会自己看一眼，
抽错了用户会直接照着做。

**验证**
改完 04 号用例从 `2026-11-18 09:00` 变成 `2026-11-22 23:59`，正确。
顺带发现 `24:00` 之前解析不了（`hour > 23` 被否掉），补了一条按当日 23:59 处理。

**影响**
顺着这个思路又加了三类负向语义：起始语（`自…起`）、活动安排语（`定于…举行`）、
区间起点。附近没有强锚点时直接剔除候选，全被剔除就返回 `None` —— 宁可空着，
也不给一个会被照做的错日期。

## 4. 准确率 100% 了，界面还是错的

**我的提问**

评测三项都 100% 了，是不是可以交作业了？

**AI 的判断**

跑一次截图看看。结果四个问题，评测一个都没抓到：

| 问题 | 为什么评测抓不到 |
|---|---|
| 解析完的空态提示还叠在结果上方 | 属于 CSS：`.empty` 的 `display:grid` 覆盖了 `hidden` 的 `display:none` |
| 「要做的事」抽出 `请表》一式两份` | `申请` 里的「请」被当成祈使句开头，正则要加前置断言 |
| `0755-8888 0000` 识别不了 | 正则要求连续数字，中间有空格 |
| 日报每天少一条收尾日志 | 汇总写在 `daily_run_end` 之前，时序问题 |

**验证**
四个都改完后重新截图核对，同时 20 条单元测试仍全绿。

**影响**
定了个规矩：**每次改完必须截图看一眼**，离线指标只覆盖解析正确性，
呈现层和时序问题它看不见。

## 5. 部署成功了，但页面是白板

**我的提问**

发布返回成功、链接也能打开，但页面一个样式都没有，控制台全是 403。
本地跑得好好的，为什么线上不行？

**AI 的判断**

平台的网关要求**每个请求**都带 `sharecode`，而浏览器加载 `<link>` / `<script>`
是独立请求，不会自动带上主页面的查询参数，于是样式表和脚本全部 403。

第一反应是"让服务端把 sharecode 注入到资源 URL 里"，试了没用——
网关转发前会把 `sharecode` 从 query 里剥掉，服务端 `parse_qs` 拿到的是空字符串。

**最后的解法**
两条一起上：

1. 云端模式把 CSS/JS **内联进 HTML**，整页只发一次请求，绕开静态资源鉴权
2. 后续 `fetch` 由前端从 `location.search` 取 `sharecode` 自己拼（浏览器地址栏里还在）

**验证**
线上截图确认：样式完整、解析正常、统计面板有数。
本地模式（无 `PORT` 环境变量）仍走外链，不影响调试。

**影响**
`app.py` 里现在有 `IN_CLOUD` 开关，两条路径分开维护。
顺带发现线上版的隐私文案不能照抄本地（"原文只在本机处理"在线上是假话），一并改了。

## 6. 100% 是不是过拟合？

**我的提问**

准确率 100% 看着挺好，但这 8 条语料是我自己写的，等于自己出题自己考。
这个数字有意义吗？

**AI 的判断**

意义有限，必须说清楚。8 条语料只能证明"在这几种写法上稳定"，
不能证明泛化。真正可信的做法是：**先补语料到 `data/samples/`，再改代码**，
否则每次都能把数字调到 100%，但只是把答案背下来了。

另外 `tests/golden.json` 是标准答案，不能为了提高分数去改它——那是调答案，不是修 bug。

**验证**
`CHANGELOG.md` 里 v0.3.0 那节写明了这句话：
"100% 只证明在这批写法上稳定，不代表泛化能力"。

**影响**
后续每一天的流程固定成：**先有真实通知样本 → 补进语料 → 跑评测看到失败 →
再改代码**。这样数字才有意义。

## 走过的弯路

| 尝试 | 为什么放弃 |
|---|---|
| 用一个大正则套地点 | 起点不可控，抽出 `00前将以下材料交至行政楼` 这种脏值 |
| 服务端注入 sharecode 到静态资源 | 网关转发前会剥掉 query，服务端根本读不到 |
| 用 LLM API 做通知解析 | 要联网、要密钥、有隐私风险，而且一条通知调一次 API 太重；规则引擎在这个场景够用 |
| 直接生成 7 天日志 | 见第 1 条，三处时间证据对不上 |

**结论留一句**：这个项目里最容易犯的错不是"抽不出来"，而是**抽错了但看起来很正常**。
所以宁可返回"未识别"，也不给一个会被照着执行的错误日期。
